# Markdown設計書ジェネレーター システム設計書

## 1. 文書情報

| 項目 | 内容 |
| --- | --- |
| システム名 | Markdown設計書ジェネレーター |
| リポジトリ | `zony21/docs-generator` |
| 対象 | 一機能単位の設計書作成 |
| 文書種別 | システム設計書 |
| 初期方針 | 小規模なブラウザ完結型ツール |

## 2. 目的

これまでExcelで作成していた設計書を、最初からMarkdownで作成・管理できるようにする。

人間がMarkdownファイルを一から手作業するのではなく、必要な設計書を選択し、必要項目を入力することで、一機能分の設計書パッケージを生成できるツールを提供する。

主な目的は次のとおり。

- 設計書作成時の定型入力を減らす。
- 設計書ごとの構成や見出しを統一する。
- 共通情報の重複入力をなくす。
- 必要な設計書だけを選択して生成できるようにする。
- 出力後のMarkdownを、そのまま正式な設計書として利用できるようにする。

## 3. 前提の変更

本ツールでは、Excelを原本としてMarkdownへ変換する運用を行わない。

```text
従来
Excel設計書を作成
    ↓
Markdownへ変換

今後
必要項目をツールへ入力
    ↓
Markdown設計書を直接生成
    ↓
Markdownを原本として管理
```

したがって、生成ファイルには次のようなExcel変換用の情報を要求しない。

- Source workbook
- Source sheet
- Original extraction file
- Extracted at

これらの代わりに、機能ID、機能名、版数、作成日、更新日、作成者など、設計書そのものの管理情報を出力する。

## 4. 対象範囲

### 4.1 初期実装の対象

初期実装では、次の機能だけを対象とする。

1. 一機能分の基本情報入力
2. 作成する設計書の選択
3. 設計書ごとの項目入力
4. 共通情報の自動反映
5. Markdownプレビュー
6. Markdown一括生成
7. ZIPファイルとしてダウンロード
8. ブラウザ内への入力途中データ保存

### 4.2 初期実装の対象外

規模を抑えるため、次の機能は初期実装に含めない。

- ユーザー登録、ログイン、権限管理
- サーバー側データベース
- 複数人の同時編集
- GitHubへの自動コミット、Pull Request作成
- Excelの読み込み、解析、変換
- AIによる要件補完や設計内容の自動生成
- WYSIWYG形式の高度なMarkdownエディター
- 図形を自由配置する画面レイアウトエディター
- 複数機能をまとめたプロジェクト管理
- 設計書の承認ワークフロー
- 独自DSLや複雑なテンプレートエンジン

## 5. 基本方針

### 5.1 一機能単位で生成する

一度の操作で、一機能分の設計書パッケージを生成する。

機能間の統合管理は行わず、生成後のMarkdownファイルをGitで管理する。

### 5.2 必要な設計書だけを作成する

すべてのテンプレートを毎回生成しない。

基本設計書は既定で選択状態にし、機能に不要なものは利用者が解除できる。条件付き設計書は、必要な場合だけ選択する。

### 5.3 共通項目は一度だけ入力する

システム名、モジュール名、機能ID、機能名、版数、作成者などは、機能基本情報として一度だけ入力し、すべての設計書へ自動反映する。

### 5.4 入力操作を減らす

- 基本6設計書を初期選択する。
- 空欄の任意項目は出力しない。
- 表の行は追加ボタンで増やせるようにする。
- 前行を複製できるようにする。
- 項番は自動採番する。
- 日付は当日を初期値とする。
- 入力途中の内容を自動保存する。
- 一度入力した共通情報を再入力させない。

## 6. 生成対象の設計書

### 6.1 基本設計書

次の6ファイルは、設計書選択画面で初期選択状態とする。

| ファイル | 役割 |
| --- | --- |
| `Hist.md` | 改訂履歴 |
| `Outline_A.md` | 目的、対象範囲、概要フロー、前提条件 |
| `Outline_B.md` | 処理分類、CRUD、関連テーブル、制約 |
| `FuncSpec.md` | 機能単位、トリガー単位の機能仕様 |
| `FuncDetail.md` | 処理単位の詳細フロー |
| `Relation.md` | データ転送元、転送先、SQL、入出力関係 |

基本設計書であっても、利用者が不要と判断した場合は選択を解除できる。

### 6.2 条件付き設計書

| ファイル | 選択する条件 |
| --- | --- |
| `S-Layout.md` | 画面項目や画面領域を定義する場合 |
| `R-Layout.md` | 帳票、ファイル、一覧結果などの出力レイアウトを定義する場合 |
| `Event.md` | 独立したイベント一覧が必要な場合 |
| `Check.md` | 入力チェックや業務チェックを定義する場合 |
| `Others.md` | 共通定数、選択肢、キー割当などがある場合 |
| `Footnote.md` | 用語、略称、コード、注釈を定義する場合 |

## 7. 出力構成

一機能につき、次の構成で出力する。

```text
<FunctionId>_<FunctionName>/
├── README.md
└── sheets/
    ├── Hist.md
    ├── Outline_A.md
    ├── Outline_B.md
    ├── FuncSpec.md
    ├── FuncDetail.md
    ├── Relation.md
    └── 選択された追加設計書.md
```

### 7.1 README.md

`README.md` はパッケージ直下に生成する。

記載内容は次のとおり。

1. 機能名
2. 機能概要
3. 文書管理情報
4. 生成した設計書の索引
5. 補足事項

索引には、実際に生成したファイルだけを掲載する。

### 7.2 sheetsフォルダ

`README.md` 以外の設計書はすべて `sheets` フォルダ内へ生成する。

## 8. 生成Markdownの共通構造

各設計書には、原則として次の共通構造を使用する。

```markdown
# <設計書名または機能名>

## 1. Document metadata

## 2. Common metadata

## 3. Document summary

## 4. Main content
```

Excel変換用テンプレートに存在していた `Blank / N/A handling` は、生成された正式設計書には出力しない。

未入力の任意項目や空の説明文も原則として出力しない。ただし、利用者が作成対象として選択した表については、列見出しのみの空表を出力できる。

## 9. 入力項目

### 9.1 機能共通情報

| 項目 | 必須 | 初期値・動作 |
| --- | --- | --- |
| システム名 | 必須 | 前回入力値を再利用可能 |
| モジュール名 | 任意 | 前回入力値を再利用可能 |
| モジュールID | 任意 | なし |
| 機能ID | 必須 | なし |
| 機能名 | 必須 | なし |
| 機能概要 | 必須 | なし |
| 文書番号 | 任意 | なし |
| 版数 | 必須 | `0.1` |
| 作成日 | 必須 | 当日 |
| 更新日 | 任意 | 当日 |
| 作成者 | 必須 | 前回入力値を再利用可能 |
| 備考 | 任意 | なし |

### 9.2 設計書選択

チェックボックスで生成対象を選択する。

- 基本6設計書は初期選択状態
- 条件付き6設計書は初期未選択
- 全選択、基本のみ、全解除を用意

### 9.3 設計書固有情報

設計書を選択した場合だけ、その設計書の入力領域を表示する。

入力領域はタブを増やさず、縦方向の折りたたみセクションとして表示する。これにより画面構成と状態管理を単純にする。

## 10. 画面設計

初期実装は1画面のシングルページとする。

```text
+--------------------------------------------------+
| Markdown設計書ジェネレーター                    |
+--------------------------------------------------+
| 1. 機能基本情報                                 |
|   システム名、機能ID、機能名、版数、作成者など |
+--------------------------------------------------+
| 2. 作成する設計書                               |
|   [x] Hist [x] Outline_A ... [ ] Check          |
+--------------------------------------------------+
| 3. 設計内容                                     |
|   ▼ Hist                                        |
|   ▼ Outline_A                                   |
|   ▼ FuncSpec                                    |
|   ...                                           |
+--------------------------------------------------+
| 4. プレビュー                                   |
+--------------------------------------------------+
| [下書き保存] [入力クリア] [ZIP出力]             |
+--------------------------------------------------+
```

### 10.1 画面遷移

画面遷移は設けない。

入力、プレビュー、出力を同一画面で完結させる。

### 10.2 入力部品

- 1行文字列: text input
- 複数行文章: textarea
- 選択: checkboxまたはselect
- 一覧形式: 編集可能な簡易テーブル
- SQL: 等幅フォントのtextarea
- フロー: 1行1ステップのtextareaまたは行追加式リスト

高度なリッチテキストエディターは使用しない。

## 11. 設計書別の入力概要

### 11.1 Hist

- 改訂日
- 作成者
- Rev.
- 対象設計書・対象領域
- 変更内容
- 承認日
- 承認者

初回生成時は、共通情報から1行を自動作成できる。

### 11.2 Outline_A

- 目的
- 対象範囲
- 対象ユーザー・対象処理
- 概要フロー
- 前提条件
- 後続条件

### 11.3 Outline_B

- 処理方式・処理分類
- CRUD・操作区分
- 関連テーブル・マスタ・インターフェース
- 制約・備考

### 11.4 FuncSpec

複数の機能仕様行を追加できる。

- 機能単位
- トリガー・タイミング
- 処理目的
- 主な手順
- 正常時の動作
- エラー・中断時の動作

### 11.5 FuncDetail

複数の処理単位を追加できる。

- 処理名
- 関数・メソッド名
- 関数種別
- 概要
- 通常処理
- 例外処理
- 終了処理
- 関連設計書

`try / catch / finally` は固定入力必須にせず、必要な場合だけ入力する。

### 11.6 Relation

複数のデータ関係を追加できる。

- 転送元
- 転送元条件
- 転送先
- 転送先条件
- SQL
- 備考

転送元と転送先は出力時に明確に分離する。

### 11.7 S-Layout

- 画面領域
- コントロール一覧
- 桁数・形式
- 必須
- デフォルト値
- 表示・編集ルール

初期実装では、画面イメージの描画機能は持たない。

### 11.8 R-Layout

- レイアウト領域
- 出力項目
- 型
- 幅
- 配置
- 形式
- 出力時の注意事項

### 11.9 Event

- イベント名
- トリガー
- 対象機能・対象処理
- 備考

### 11.10 Check

- チェック対象
- チェック名
- タイミング
- チェック項目
- 種別
- 詳細
- メッセージID
- メッセージ引数

### 11.11 Others

- 共通定数
- 選択肢
- ファンクションキー割当
- 補助マッピング
- 運用上の補足

### 11.12 Footnote

- 用語
- 説明
- 略称・コード
- 定義
- 補足注記

## 12. データモデル

初期実装では、フォーム状態を1つのJSONオブジェクトとして保持する。

```ts
interface DesignPackage {
  schemaVersion: string;
  common: CommonMetadata;
  selectedDocuments: DocumentType[];
  documents: {
    hist?: HistDocument;
    outlineA?: OutlineADocument;
    outlineB?: OutlineBDocument;
    screenLayout?: ScreenLayoutDocument;
    reportLayout?: ReportLayoutDocument;
    funcSpec?: FuncSpecDocument;
    event?: EventDocument;
    funcDetail?: FuncDetailDocument;
    relation?: RelationDocument;
    check?: CheckDocument;
    others?: OthersDocument;
    footnote?: FootnoteDocument;
  };
}
```

データ構造は永続化形式と画面状態で共用し、変換用の複雑な中間モデルは作らない。

## 13. システム構成

### 13.1 採用構成

初期実装は次の構成とする。

- Vite
- TypeScript
- HTML
- CSS
- JSZip
- Browser Local Storage

フロントエンドフレームワークは使用しない。

### 13.2 構成理由

- サーバーを用意せずに利用できる。
- 配布や起動が簡単である。
- データを外部へ送信しない。
- 実装ファイル数と依存関係を抑えられる。
- Markdown生成処理をTypeScriptの純粋関数として実装できる。
- 将来必要になった場合でも、ReactやVueへ移行しやすい。

### 13.3 想定ファイル構成

```text
/
├── docs/
├── index.html
├── package.json
├── tsconfig.json
├── src/
│   ├── main.ts
│   ├── model.ts
│   ├── documentDefinitions.ts
│   ├── markdownGenerator.ts
│   ├── storage.ts
│   └── style.css
└── tests/
    └── markdownGenerator.test.ts
```

画面部品を細かく分割しすぎず、初期段階では上記程度に抑える。

## 14. 処理フロー

```text
画面起動
  ↓
Local Storageから下書きを読み込む
  ↓
機能共通情報を入力
  ↓
設計書を選択
  ↓
選択された設計書の内容を入力
  ↓
入力値をJSON状態へ反映
  ↓
Markdown生成関数を実行
  ↓
プレビュー表示
  ↓
README.mdと選択済み設計書を生成
  ↓
ZIPへ格納してダウンロード
```

## 15. Markdown生成ルール

1. `README.md` 以外は必ず `sheets/` 配下へ出力する。
2. READMEの索引には、選択された設計書だけを掲載する。
3. 見出し順は設計書定義で固定する。
4. 共通情報はすべての設計書へ自動反映する。
5. 任意項目が未入力の場合、その項目自体を出力しない。
6. 空の表は原則出力しない。
7. 利用者が表枠の出力を指定した場合だけ、見出しのみを出力する。
8. 複数行SQLは `sql` フェンスで囲む。
9. Markdown表内の `|` と改行はエスケープする。
10. ファイル名に利用できない文字は `_` へ置換する。
11. 文字コードはUTF-8とする。
12. AIによる内容の補完や推測は行わない。

## 16. 自動保存

入力状態をLocal Storageへ保存する。

- 入力変更後に一定の短い間隔で保存する。
- 保存対象は `DesignPackage` 全体とする。
- 「入力クリア」で保存データも削除する。
- 保存形式には `schemaVersion` を持たせる。

複数下書きの管理は初期実装に含めず、保存スロットは1件だけとする。

## 17. バリデーション

ZIP出力時に、最低限次を確認する。

- 機能IDが入力されている。
- 機能名が入力されている。
- システム名が入力されている。
- 作成者が入力されている。
- 版数が入力されている。
- 1つ以上の設計書が選択されている。
- 選択された設計書に最低限必要な内容がある。

入力中は警告表示に留め、出力時に必須エラーを確定する。

## 18. 非機能要件

### 18.1 対応環境

- 最新版のChrome、Edge、Safari
- PC画面を主対象とする

### 18.2 セキュリティ

- 入力内容を外部サーバーへ送信しない。
- ブラウザ上だけでMarkdownとZIPを生成する。
- HTMLプレビュー時は入力文字列をエスケープする。

### 18.3 性能

一機能分の設計書を対象とし、通常の入力操作とMarkdown生成が待ち時間なく実行できること。

### 18.4 保守性

- 設計書ごとの出力処理を関数単位で分離する。
- 画面上の項目定義とMarkdown出力定義を可能な範囲で共通化する。
- 過度な汎用テンプレートエンジンは作らない。

## 19. 受け入れ条件

初期実装は、次を満たした時点で完成とする。

1. 一機能の共通情報を入力できる。
2. 基本6設計書が初期選択される。
3. 条件付き6設計書を追加選択できる。
4. 選択した設計書だけ入力領域が表示される。
5. 共通情報が各Markdownへ反映される。
6. READMEと選択済み設計書が正しいフォルダ構成で生成される。
7. READMEの索引と生成ファイルが一致する。
8. SQLがコードブロックとして出力される。
9. 未入力の任意項目が不要なプレースホルダーとして残らない。
10. ZIPファイルをダウンロードできる。
11. 画面再読み込み後も直前の下書きを復元できる。
12. サーバーやデータベースなしで動作する。
