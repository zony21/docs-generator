# Docs Generator 要件定義書

## 1. 背景

今後は、ExcelではなくMarkdownを正式な設計書として取り扱う。

そのため、Excelを先に作成してMarkdownへ変換する工程は不要となる。一方で、各設計書を人間が一から手作業で作成すると、ファイル作成、見出し記述、共通情報の転記、表の整形、リンク作成などに時間がかかる。

Docs Generatorは、必要項目を選択・入力することで、一機能分のMarkdown設計書パッケージを効率よく生成するためのツールとする。

## 2. 目的

- 一機能分の設計書を、Excelを介さずMarkdownとして直接生成する。
- 設計者が内容の検討と記入に集中できるよう、定型作業を自動化する。
- 機能種別に応じて必要な設計書を選択できるようにする。
- 共通メタデータや重複情報を一度の入力で複数設計書へ反映する。
- 出力形式を統一し、レビュー、差分確認、Git管理、AI利用を容易にする。

## 3. 対象範囲

### 3.1 対象

- 一機能単位の設計書パッケージ作成
- 新規設計書の作成
- 入力途中データの保存と再開
- 生成前プレビュー
- 入力内容の検証
- Markdownファイル一式の出力
- ZIP形式での一括ダウンロード
- 既存の生成済みMarkdownパッケージの再読込と編集

### 3.2 初期リリースで対象外

- Excelからの自動変換
- ソースコードからの設計書自動生成
- AIによる要件の自動補完
- 複数人のリアルタイム共同編集
- 承認ワークフロー
- GitHubへの直接コミット
- サーバー側での永続保存

これらは将来拡張候補とし、初期実装には含めない。

## 4. 利用者

| 利用者 | 主な利用目的 |
| --- | --- |
| 設計担当者 | 必要項目を入力し、設計書一式を生成する |
| 実装担当者 | 出力された設計書を参照して実装する |
| レビュー担当者 | Markdown差分と設計内容を確認する |
| AIエージェント | 定型構造の設計書を読み取り、実装やレビューに利用する |

## 5. 基本業務フロー

1. 新しい機能設計を開始する。
2. プロジェクトと機能の共通情報を入力する。
3. 機能種別を選択する。
4. ツールが基本設計書と推奨設計書を選択する。
5. 利用者が必要な設計書を追加・解除する。
6. 設計書ごとの入力フォームへ内容を記入する。
7. ツールが共通情報、参照リンク、履歴の初期値を自動反映する。
8. プレビューと検証結果を確認する。
9. 一機能分のMarkdownパッケージをZIPまたはフォルダとして出力する。
10. 以後は出力されたMarkdownを正式な設計書として管理する。

## 6. 機能要件

### 6.1 新規機能設計の作成

利用者は、次の情報を入力して新規設計を開始できること。

- システム名
- モジュール名
- モジュールID
- 機能ID
- 機能名
- 機能種別
- 作成者
- 作成日
- Rev
- 文書番号
- 概要

### 6.2 機能種別

初期実装では、次の機能種別を選択可能とする。

- 画面
- API
- バッチ
- 帳票
- 共通機能
- その他

機能種別は、設計書の初期選択と入力フォームの表示制御に使用する。

### 6.3 設計書選択

基本設計書は初期状態で選択済みとする。

- `Hist.md`
- `Outline_A.md`
- `Outline_B.md`
- `FuncSpec.md`
- `FuncDetail.md`
- `Relation.md`

条件付き設計書は、機能種別と入力内容から推奨する。

- `S-Layout.md`
- `R-Layout.md`
- `Event.md`
- `Check.md`
- `Others.md`
- `Footnote.md`

利用者は推奨結果を変更できること。ただし、基本設計書を解除する場合は警告を表示する。

### 6.4 共通項目の自動反映

共通メタデータは一度だけ入力し、選択された全設計書へ反映する。

同じ情報を複数画面で再入力させないこと。

### 6.5 設計書入力

各設計書は、テンプレートに対応する専用フォームを持つこと。

- 単一行テキスト
- 複数行テキスト
- 選択項目
- チェックボックス
- 繰り返し可能な表形式入力
- 並び替え可能な処理ステップ
- SQL入力欄
- 相互参照の選択

表形式入力は、行追加、行削除、複製、並び替えを可能とする。

### 6.6 入力支援

操作回数を減らすため、次を実装する。

- 前回使用した共通メタデータの再利用
- プロジェクトプリセット
- 機能種別ごとの設計書プリセット
- 初期値の自動設定
- 作成日の自動入力
- Revの初期値設定
- `Hist.md` 初回行の自動生成
- 機能名や機能IDの各設計書への自動反映
- 設計書間で共通する入力内容の同期
- キーボードによる入力欄移動
- 入力内容の自動保存
- 既存機能の複製作成

### 6.7 プレビュー

生成されるMarkdownを、ファイル単位でリアルタイムに確認できること。

- READMEプレビュー
- 各設計書プレビュー
- Markdownソース表示
- レンダリング表示
- ファイル切替

### 6.8 検証

出力前に、次を検証する。

- 必須項目の不足
- 選択済み設計書に必要な主要情報の不足
- ファイル名に使用できない文字
- 重複する機能ID
- 空の表行
- 壊れた相互参照リンク
- README索引と生成対象ファイルの不一致
- SQLコードブロックの不整合

エラーは出力を停止し、警告は確認後に出力可能とする。

### 6.9 出力

一機能につき、次の形式で出力する。

```text
<機能ID>_<機能名>/
├── README.md
└── sheets/
    └── 選択された設計書.md
```

出力要件は次のとおり。

- 文字コードはUTF-8
- 改行コードはLFを標準とする
- README以外はすべて`sheets`配下に配置する
- README索引には実際に生成したファイルだけを掲載する
- 未選択の設計書は生成しない
- 不要な空ファイルを生成しない
- Markdown内の相対リンクを正しく生成する
- ZIPダウンロードを提供する
- 対応ブラウザではフォルダへの直接保存を提供する

### 6.10 再編集

生成済みパッケージを読み込み、フォームへ復元できること。

Markdownが正式な設計書であるため、再編集時はMarkdownを入力元として扱う。

初期実装では、本ツールが生成した規定形式のMarkdownのみを完全対応対象とする。手作業で大幅に構造変更されたMarkdownは、読込警告または部分読込として扱う。

## 7. 非機能要件

### 7.1 利便性

- 初回利用者が説明なしでも基本操作を理解できること。
- 一機能の新規作成開始までを3操作以内にする。
- 共通情報の重複入力を発生させないこと。
- 保存操作を意識せず作業を継続できること。

### 7.2 性能

- 通常の入力操作は100ms以内を目標に画面反映する。
- Markdownプレビュー更新は500ms以内を目標とする。
- 12種類すべての設計書を含むパッケージを3秒以内に生成することを目標とする。

### 7.3 可用性

- 初期実装はローカルファーストとし、ネットワーク接続なしでも利用可能とする。
- ブラウザを閉じても入力途中データを復元可能とする。

### 7.4 セキュリティ

- 初期実装では設計内容を外部サーバーへ送信しない。
- 入力データはブラウザ内に保存する。
- Markdownプレビューでは任意HTMLとスクリプトを無効化する。

### 7.5 保守性

- 設計書テンプレートを追加しやすい構成とする。
- フォーム定義とMarkdown生成処理を分離する。
- 各設計書の生成処理を独立してテスト可能とする。

## 8. 制約

- Markdownの構造は提供済みテンプレートを基準とする。
- Excel由来の項目は、Markdown直接作成に合う名称へ変更する。
- AIが不足要件を自動生成する機能は初期実装に含めない。
- 設計者が入力した内容を、意味が変わる形で自動修正しない。

## 9. 受入条件

- 一機能分の新規設計を作成できる。
- 基本6設計書が初期選択される。
- 機能種別に応じて条件付き設計書が推奨される。
- 共通メタデータを一度の入力で全ファイルへ反映できる。
- 選択した設計書だけが生成される。
- README以外がすべて`sheets`配下に配置される。
- README索引と実ファイルが一致する。
- Markdownプレビューを確認できる。
- 入力不足やリンク不整合が検出される。
- ZIPとしてダウンロードできる。
- 自動保存した作業を再開できる。
- 本ツールで生成したMarkdownパッケージを再読込できる。
