# Markdown設計書ジェネレーター 実装計画

## 1. 文書情報

| 項目 | 内容 |
| --- | --- |
| システム名 | Markdown設計書ジェネレーター |
| リポジトリ | `zony21/docs-generator` |
| 文書種別 | 実装計画 |
| 対象 | 一機能単位のMarkdown設計書生成 |
| 方針 | テンプレート準拠・小規模・ブラウザ完結 |

## 2. 実装目標

利用者が必要な設計書を選択し、必要項目だけを入力することで、一機能分のMarkdown設計書パッケージを生成できるようにする。

生成物はExcel変換後の中間資料ではなく、正式な設計書として利用する。

初期完成時に必要な機能は次のとおり。

1. 機能共通情報の入力
2. 生成する設計書の選択
3. 設計書固有項目の入力
4. Markdownプレビュー
5. `README.md` と `sheets/*.md` の生成
6. ZIPダウンロード
7. 入力途中データの自動保存

## 3. テンプレート優先方針

### 3.1 テンプレートを出力形式の正本とする

リポジトリの次のファイルを、生成形式の正本とする。

```text
templates/
├── README_TEMPLATE.md
└── sheets/
    ├── Hist.md
    ├── Outline_A.md
    ├── Outline_B.md
    ├── S-Layout.md
    ├── R-Layout.md
    ├── FuncSpec.md
    ├── Event.md
    ├── FuncDetail.md
    ├── Relation.md
    ├── Check.md
    ├── Others.md
    └── Footnote.md
```

見出し、項目順、表の列、ファイル名は、原則としてテンプレートに従う。

### 3.2 テンプレートへの差し込み

テンプレートには、次のような単純な置換トークンを配置する。

```text
{{SYSTEM_NAME}}
{{FUNCTION_ID}}
{{FUNCTION_NAME}}
{{HIST_ROWS}}
{{SQL_BLOCKS}}
```

スカラー値は文字列置換する。

表、処理ブロック、SQLなどの繰り返し項目は、TypeScript側でMarkdown文字列を作成し、対応するブロックトークンへ差し込む。

### 3.3 複雑なテンプレートエンジンを作らない

初期実装では、条件分岐や繰り返し構文を持つ独自テンプレート言語を作成しない。

- 単一値: 単純置換
- 表: Markdown行を生成して差し込み
- 複数処理: Markdownブロックを生成して差し込み
- 未入力値: 空文字または既定文へ置換

これにより、提供されたテンプレートとほぼ同じ設計書を生成しながら、実装を小さく保つ。

## 4. 実装規模を抑える制約

初期実装では、次を行わない。

- バックエンドの作成
- データベースの導入
- ログイン、権限管理
- 複数人同時編集
- GitHubへの自動コミット
- Excelの読み込み、変換
- AIによる設計内容の補完
- 高機能なWYSIWYGエディター
- 自由配置式の画面レイアウト作成
- 複数プロジェクト、複数機能の管理
- テンプレートを画面上で編集する機能
- 複数下書きの保存
- 複雑なプラグイン機構

## 5. 採用技術

| 区分 | 採用内容 |
| --- | --- |
| ビルド | Vite |
| 言語 | TypeScript |
| UI | HTML、CSS、DOM API |
| テンプレート読込 | Vite raw import |
| ZIP生成 | JSZip |
| 下書き保存 | Local Storage |
| テスト | Vitest |

ReactやVueは初期実装では使用しない。

## 7. 実装ステップ

## Step 1. 開発基盤とテンプレート検証

### 作業内容

1. Vite + TypeScriptプロジェクトを作成する。
2. JSZipとVitestを追加する。
3. `templates/` 配下の全テンプレートをraw文字列として読み込めるようにする。
4. テンプレートのファイル一覧を定義する。
5. 必須トークンが存在することを検証するテストを作成する。

### 完了条件

- 開発サーバーが起動する。
- 13個のテンプレートを読み込める。
- 欠落テンプレートと重複トークンを検出できる。

## Step 2. データモデルと共通入力

### 作業内容

1. `DesignPackage` 型を作成する。
2. 共通情報入力欄を作成する。
3. 基本6設計書を初期選択する。
4. 条件付き6設計書を選択できるようにする。
5. 選択状態に応じて入力セクションを表示・非表示にする。

### 共通入力項目

- システム名
- モジュール名
- モジュールID
- 機能ID
- 機能名
- 機能概要
- 文書番号
- 日付
- Rev
- 作成者
- 備考

### 完了条件

- 共通情報を一度だけ入力できる。
- 基本6設計書が初期選択される。
- 全選択、基本のみ、全解除が動作する。

## Step 3. 設計書固有フォーム

### 作業内容

12種類の設計書について、テンプレートの項目と対応する入力欄を作成する。

基本6設計書を先に実装し、動作確認後に条件付き6設計書を追加する。

### 入力形式

- 単一行: `input`
- 複数行: `textarea`
- 表: 行追加式の簡易テーブル
- 手順: 1行1ステップのリスト
- SQL: 等幅フォントの`textarea`

### 操作削減

- 行追加
- 行削除
- 前行複製
- 上下移動
- No.の自動採番
- 初回履歴行の自動作成

ドラッグ&ドロップは実装しない。

### 完了条件

- 選択した設計書だけ入力できる。
- 各入力項目がテンプレート上のトークンと対応する。
- 行の追加、削除、複製ができる。

## Step 4. Markdown生成とプレビュー

### 作業内容

1. 共通トークンを置換する。
2. 設計書別の表行をMarkdownへ変換する。
3. 複数処理をMarkdownブロックへ変換する。
4. SQLを`sql`コードフェンスへ変換する。
5. READMEの索引行を選択済み設計書から生成する。
6. 生成結果を画面上でプレビューする。

### 生成ルール

- README以外は必ず`sheets/`配下とする。
- 選択していない設計書は生成しない。
- 見出しと表構造はテンプレートを維持する。
- Markdown表内の`|`と改行をエスケープする。
- 入力値から要件を推測しない。
- テンプレートに未置換トークンを残さない。

### 完了条件

- 基本6設計書がテンプレートと同じ構造で出力される。
- 条件付き設計書も選択時だけ出力される。
- README索引と出力ファイルが一致する。
- 未置換トークンが存在する場合は出力を停止できる。

## Step 5. ZIP出力、自動保存、仕上げ

### 作業内容

1. 出力ファイルをJSZipへ追加する。
2. `<FunctionId>_<FunctionName>.zip`を生成する。
3. Local Storageへ入力状態を自動保存する。
4. 再読み込み時に下書きを復元する。
5. 入力クリア機能を作成する。
6. 出力前バリデーションを実装する。
7. READMEと利用手順を作成する。

### 完了条件

- 正しいフォルダ構成のZIPをダウンロードできる。
- 再読み込み後も入力内容が復元される。
- 必須項目不足時に出力されない。
- サーバーなしで利用できる。

## 9. テスト計画

### 9.1 テンプレート検証

- 13個のテンプレートが存在する。
- 各テンプレートに共通トークンが存在する。
- READMEに`SHEET_INDEX_ROWS`が存在する。
- 各設計書に必要な固有ブロックトークンが存在する。

### 9.2 Markdown生成

- 共通情報が正しく置換される。
- 表の列順がテンプレートと一致する。
- 複数行SQLがコードフェンスで囲まれる。
- `|`を含む入力値が表を壊さない。
- 未入力任意項目の扱いが統一される。
- 未置換トークンを検出できる。

### 9.3 ZIP出力

- ルートに`README.md`だけが存在する。
- 設計書が`sheets/`配下へ入る。
- 選択した設計書だけが含まれる。
- README索引のリンク先がZIP内に存在する。

## 10. 受け入れ条件

1. 一機能分の設計書を作成できる。
2. 基本6設計書が初期選択される。
3. 条件付き6設計書を追加選択できる。
4. 共通情報を一度だけ入力すればよい。
5. 提供されたテンプレートとほぼ同じ見出し、表、並び順で生成される。
6. README以外はすべて`sheets/`へ出力される。
7. README索引は実際の生成ファイルと一致する。
8. ZIPで一括取得できる。
9. 入力状態を自動保存できる。
10. バックエンドなしで動作する。
11. 未置換トークンや必須不足を検出できる。
12. AIによる設計内容の補完を行わない。
